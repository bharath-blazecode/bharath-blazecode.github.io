01Context

The project and my contribution

ClassQuest turns course material into playable challenges: make a prediction, diagnose the result, check source evidence, then apply the idea or try again. Learners join a cohort server and receive readiness feedback based on the group’s answers. We built it with React, TypeScript, FastAPI, Python and SQLite.

Miguel Pineda led the technical build for our five-person team. My work covered the playable demo, frontend foundation, upload security and cohort features, and I presented during the judging Q&A. The team received the People’s Choice Award following audience voting across 15 teams.

I was a Code Network Event Officer while competing in its hackathon. The executive cleared this before the event.

One decision

PR #12
Merged 22 Aug 2026

A filename is a label. It should not choose a path.

I changed the upload handler so the server chooses where a file is stored, while keeping its original name for display. I also bounded the application read and added regression tests. The useful part is the boundary: a familiar label should not decide where bytes get written.

My patch, within a five-person team’s build. Miguel Pineda led the technical work; the People’s Choice Award belongs to the team.

01 / Before

One name. Two jobs.

The original handler joined the supplied filename to the upload directory. A path-like name could steer that join outside the intended folder. It also read the entire file before checking its size.

Two lines from the old handler
data = f.file.read()
path = doc_dir / filename

Non-adjacent lines; read them in context (external site).

02 / The change

Keep the label. Choose the path.

The generated document ID becomes the storage name; the original filename stays in the database as display metadata. Inspect the storage change (external site)

The extra byte

It is enough to tell whether the file is too large. The helper asks for at most limit + 1 bytes, then returns HTTP 413 (“too large”) if it got more than the limit. A file exactly at the limit still works.

data = file.file.read(max_bytes + 1)
if len(data) > max_bytes:
    raise HTTPException(...)

Excerpt; exception arguments shortened. Read the full helper (external site)

03 / What backs it

A change you can check for yourself.

Three added test functions cover four cases. The filename test runs twice; each case also checks the original label and stored bytes are preserved.

  1. 01
    A relative path as a filename

    ../outside.txt stays metadata. The stored file remains inside the server’s upload directory.

  2. 02
    An absolute path as a filename

    /tmp/outside.txt also cannot choose the storage destination.

  3. 03
    Read just enough to reject

    With 9 bytes available and a 5-byte limit, the read requests 6 bytes and returns HTTP 413.

  4. 04
    Accept the boundary

    Five bytes at a 5-byte limit are accepted. The limit does not reject a file that fits.

Read the four cases in the merged patch (external site)

A focused fix, with more to do.

This patch did not add malware scanning, parser isolation or upstream request limits before multipart parsing. It bounds this application read; it does not make the whole upload pipeline safe or prevent every kind of resource exhaustion. See the recorded scope and deferred work (external site)

03What broke

Three problems found during the build

  1. A failed typecheck left a broken card in the hub. An upstream change invalidated a dependent component, and we moved past the type error under time pressure. Testing exposed the broken card later.
  2. The first onboarding forced a learning mode on people. The team already understood the modes, which made the forced choice seem clearer to us than it was to new users. We removed that step.
  3. The upload handler was insecure in its first version. It used client-supplied filenames for storage and read each whole file before checking its size. I separated the storage name from the label, bounded that read and added regression tests.
04What I’d change

What I would do earlier

  1. Start with safe upload defaults. Server-generated identifiers and bounded reads should have been in the first version rather than the patch.
  2. Test onboarding with someone outside the team on day one. Someone who had not been part of the planning conversation could have challenged our assumptions about the starting experience much earlier.
  3. Finish the security baseline earlier. Writing down what is unhardened is most useful while there is still time to harden some of it, not at the end as documentation.
