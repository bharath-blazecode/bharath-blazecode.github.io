From the home lab

What happens when Word spawns PowerShell

A busy endpoint produces thousands of process-creation events a day. Almost all of them are boring, which is the point: you cannot recognise the one that matters without knowing what ordinary looks like.

This is that stream, playing at real speed. Wait for it.

The rule behind it

One event, through my rule, to a response

Step through with the tabs or the arrow keys. Sample telemetry modelled on my lab; the rule is the shape I write them in.

The endpoint reports a process creation

Sysmon logs Event ID 1 on every process start. On its own this is noise. The signal lives in the parent-child relationship.

EventID 1 (Process Create) UtcTime 2026-09-07 11:42:18.221 Image C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe ParentImage C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE CommandLine powershell.exe -nop -w hidden -enc SQBFAFgAKABOAGUAdw... User DESKTOP-••••••••\barry Hashes SHA256=1B2F4C9A...E77D

Two fields carry the whole detection. A document is not supposed to start a shell, and an encoded command in a hidden window is not how anyone runs PowerShell on purpose.

The rule, in local_rules.xml

It chains off Wazuh’s built-in Sysmon process-create rule and narrows on the parent. Level 12 puts it above the noise floor so it surfaces on the dashboard instead of settling into the archive.

<group name="sysmon,windows,"> <rule id="100210" level="12"> <if_sid>61603</if_sid> <field name="win.eventdata.parentImage">WINWORD.EXE|EXCEL.EXE</field> <field name="win.eventdata.image">powershell.exe</field> <description>Office application spawned PowerShell</description> <mitre><id>T1059.001</id></mitre> </rule> </group>

The MITRE mapping matters more than it looks. It means the alert arrives carrying a name any responder already knows, rather than a description only its author understands.

Triage, in the order I work it

  1. Decode the payload. Base64 out of the encoded block first, because everything after this depends on what it was trying to do.
  2. Establish the document. Which file Word had open, where it came from, who else received it.
  3. Pull sibling events. Network connections and registry writes from the same process GUID inside the following minute.
  4. Contain or clear. Isolate the endpoint if the payload reached out. If it turns out to be a macro someone wrote in-house, the rule needs an exception, not the user a lecture.
  5. Write it down. Every tuning decision goes in the log, or the next person inherits a rule nobody can explain.

Failure log

Four things that broke, and what fixed them

Real entries from the Phase 1 build. Anyone can post a screenshot of a working dashboard.

Faults encountered building the ITDR home lab, with diagnosis and resolution.
SymptomDiagnosisFix
VM storage corrupting OneDrive was syncing the VM directory and holding locks on open .vmdk files mid-write. Moved every VM file outside the OneDrive tree. Now a standing rule for anything that writes continuously.
Server unreachable A stale netplan config held a static address of 192.168.170.10, from a subnet that stopped existing when the adapter changed. Rewrote netplan against the bridged adapter. Found by comparing the configured address to the adapter’s actual subnet rather than debugging the service on top.
Indexer stalling Virtual disk at 99% of 50 GB. The indexer degrades quietly rather than failing loudly, so it presented as a performance problem first. Expanded to 100 GB via LVM without a rebuild. Sized for retention from then on instead of for install.
SSH dead on NAT NAT networking left the host unreachable while the agent still enrolled, so the failure looked partial rather than total. Reverted to bridged to get the lab productive. NAT restoration on the correct subnet is documented and queued, not abandoned.
