Context

The project and my contribution

ClassQuest turns course material into playable challenges: make a prediction, diagnose the result, check source evidence, then apply the idea or try again. Learners join a cohort server and receive readiness feedback based on the group’s answers. We built it with React, TypeScript, FastAPI, Python and SQLite.

Miguel Pineda led the technical build for our five-person team. My work covered the playable demo, frontend foundation, upload security and cohort features, and I presented during the judging Q&A. The team received the People’s Choice Award following audience voting across 15 teams.

I was a Code Network Event Officer while competing in its hackathon. The executive cleared this before the event.

What I built

My work across ten merged pull requests

The playable learning loop

I built the prediction → diagnosis → source evidence → transfer-or-retry cycle, answer choices and concept trail. I added an overfitting fixture and updated the backend test expectations to match.

Frontend foundation and the visual system

I connected sign-in and registration to the existing API, restored returning sessions, and built onboarding and server create/join flows with loading states and error recovery. I applied the team’s visual system across those screens and the demo.

Upload security and regression tests

The original handler used client-supplied filenames as storage paths and read uploads without a limit. That allowed path traversal or file overwrite, while a large request could exhaust memory or disk.

I replaced the supplied filenames with server-generated storage identifiers, bounded the read and added tests for traversal attempts, absolute paths and size limits. I also documented the security work that remained after the hackathon.

Cohort learning and preferences

I added an asynchronous practice challenge and readiness feedback based on shared answer patterns. When the answer data is sparse or tied, the application uses a fallback rather than presenting a confident readiness judgement. Local learning preferences are validated and still work when storage is blocked.

Iteration and debugging

I revised the starting experience to remove forced learning modes, fixed a dependent hub card exposed by a failed typecheck, and added universal dashboard actions.

What broke

Three problems found during the build

  1. A failed typecheck left a broken card in the hub. An upstream change invalidated a dependent component, and we moved past the type error under time pressure. Testing exposed the broken card later.
  2. The first onboarding forced a learning mode on people. The team already understood the modes, which made the forced choice seem clearer to us than it was to new users. We removed that step.
  3. The upload handler was insecure in its first version. It accepted untrusted filenames and unbounded uploads. I corrected both and added regression tests.
What I’d change

What I would do earlier

  1. Start with safe upload defaults. Server-generated identifiers and bounded reads should have been in the first version rather than the patch.
  2. Test onboarding with someone outside the team on day one. Someone who had not been part of the planning conversation could have challenged our assumptions about the starting experience much earlier.
  3. Finish the security baseline earlier. Writing down what is unhardened is most useful while there is still time to harden some of it, not at the end as documentation.
