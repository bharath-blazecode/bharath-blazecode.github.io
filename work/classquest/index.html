ClassQuest

A learning site that turns lecture material into playable quests, built over one weekend by a team of four. It won the People’s Choice Award.

Event Code Network Winter Hackathon, 21–23 Aug 2026 Result People’s Choice Award Team Four, led technically by Miguel Pineda Stack React · TypeScript · FastAPI · Python · SQLite
Context

What it is, and what my part in it was

ClassQuest takes course material and turns it into a sequence of playable challenges: predict, diagnose, check the source evidence, then transfer the idea or retry. Students join a cohort server, work through quests, and get readiness feedback based on how the group is answering.

The honest framing on credit: this was a team project and Miguel Pineda led the technical build. I was one of the main contributors, working across the playable demo, the frontend foundation, upload security and the cohort features, and I presented during the judging Q&A. The award went to the team, not to me.

I was also an Engagement Officer for Code Network, which runs the hackathon. Competing in an event I helped organise was cleared beforehand; I mention it because leaving it out would be the more interesting omission.

What I built

Ten pull requests, grouped by what they did

The playable learning loop

Built the prediction → diagnosis → source evidence → transfer-or-retry cycle, the answer choices and the concept trail. Added an overfitting fixture and updated the backend test expectations to match.

Frontend foundation and the visual system

Connected sign-in and registration to the existing API, restored sessions on return, and built the onboarding and server create/join flows with loading and error recovery. Applied the team’s visual system across those screens and the demo.

Upload security and regression tests

This is the piece I would want asked about in an interview. The original handler used client-supplied filenames as storage paths and read uploads without a bound.

Two problems in one function. A client-controlled filename means a caller can choose where the file lands, which is path traversal in the ordinary case and file overwrite in the worse one. An unbounded read means one request can exhaust memory or disk.

The fix was to generate storage identifiers server-side and discard the supplied name entirely, and to bound the read. Then tests for traversal attempts, absolute paths and size limits, so the next person to touch it finds out immediately if they undo it. I also wrote a security baseline documenting what was still unhardened, because a weekend build has more holes than one pull request closes and pretending otherwise is worse than listing them.

Cohort learning and preferences

An asynchronous practice challenge and readiness feedback derived from shared answer patterns, with safeguards for sparse or tied evidence so the system does not make confident claims from three data points. Plus validated local learning preferences with fallbacks for when storage is blocked.

Iteration and debugging

Revised the starting experience to remove forced learning modes, fixed a dependent hub card that broke after a failed typecheck, and added universal dashboard actions.

What broke

Weekend-build realities

  1. A failed typecheck left a broken card in the hub. A change upstream invalidated a dependent component and the type error was skipped past under time pressure. It surfaced as a visibly broken card during testing rather than as a build failure, which is the expensive order to find things in.
  2. The first onboarding forced a learning mode on people. It tested fine with the team, who all knew what the modes meant, and confused everyone else. We removed the forced choice entirely.
  3. The upload handler shipped insecure first. It worked, which in a hackathon is the bar, and it was wrong. Finding it during the build rather than after is the only reason it is a story about the fix instead of a story about the incident.
What I’d change

Honest revisions

  1. Write the upload handler correctly the first time. Server-generated identifiers and a bounded read are not advanced techniques. They are the default, and I reached for them second rather than first.
  2. Test onboarding with someone outside the team on day one. Every usability problem we found late would have been found in ten minutes by one person who had not been in the planning conversation.
  3. Finish the security baseline earlier. Writing down what is unhardened is most useful while there is still time to harden some of it, not at the end as documentation.
