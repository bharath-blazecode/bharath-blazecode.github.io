LUNA

A Raspberry Pi robot where computer vision, offline voice, wireless control and PID-tuned movement all had to run at once without breaking each other.

When Jul–Nov 2025 Where QUT university project With Zhirui Lu Stack Python · OpenCV · Flask · NumPy · Tkinter · Raspberry Pi 4B
Context

A robotics unit that stopped being coursework

LUNA is built on the Hiwonder TurboPi platform around a Raspberry Pi 4B: hardware assembly, Python control software, a web interface for wireless operation, computer vision, offline voice interaction over a WonderEcho module, and PID-tuned movement. Built from the ground up with Zhirui Lu.

It started as an assessment item and became the project I actually wanted to finish. The reason is specific: I wanted to understand how a software decision turns into physical behaviour. A badly tuned control loop does not throw an exception, it makes the robot spin. A missed sensor reading does not log a warning, it ends the demonstration. That feedback is immediate and public and it keeps you honest in a way a failing unit test does not.

What I built

Four subsystems and the seams between them

The individual features were not the hard part. Line following works. Colour tracking works. A Flask interface serving control commands works. Voice recognition over I²C works. The difficulty was making all four coexist on one Pi, sharing a camera, a bus and a control loop, without any one of them starving the others.

Vision OpenCV — line following, colour tracking, tag detection Voice WonderEcho over I²C, offline recognition, no network Control Flask web interface for wireless operation Movement PID-tuned drive with mecanum wheels Interface Tkinter for local diagnostics

The integration question was the real one: how do you get independent hardware subsystems to respond reliably under real conditions, when each of them assumes it owns the loop? Most of the work was arbitration, timing and deciding what degrades gracefully when something else takes too long.

What broke

Physical failure modes

  1. Control loop tuning made it spin. PID values that looked reasonable produced overcorrection that compounded. There is no stack trace for this; you watch it and reason backwards from the behaviour.
  2. Missed sensor reads ended demonstrations. A dropped frame or a bus timeout that a desktop program would shrug off becomes a robot driving into a wall, so every read needed a defined behaviour for the case where it returns nothing.
  3. Subsystems starved each other. Vision processing at full rate left nothing for voice. Both wanted to be the thing that decided what happened next.

The habit that came out of this is the one that runs through everything else on this site: documenting decisions in real time is what saves the project when something breaks at 2am. The failure log on my home lab exists because of this robot.

What I’d change

Honest revisions

  1. Design the arbitration first. We built four subsystems and then worked out how they would share resources. The order should have been the reverse, and roughly half the integration pain came from that one decision.
  2. Instrument it from the start. There was no timing telemetry, so diagnosing starvation meant guessing and re-testing. Logging loop durations from day one would have turned a week of that into an afternoon.
  3. Define degradation explicitly. "What should this do when the camera returns nothing" is a design question, and we kept answering it accidentally, in whichever way the code happened to fall through.
