Selected work / LUNA

03 / Physical systems / Shared university project

LUNA

A small robot with several ways to listen, see and move — and a practical lesson in making those parts work together.

In a minute

A Raspberry Pi 4B robot built with Zhirui Lu at QUT, July–November 2025. LUNA combines computer vision, offline voice commands, wireless control and tuned movement on the Hiwonder TurboPi platform.

My contribution

I integrated WonderEcho voice control and voice-triggered line following, maintained and repaired the hardware, supported Flask command routing, and refined PID tuning after Zhirui’s initial implementation. We shared final integration and documentation.

Status & scope

Completed with Zhirui Lu, November 2025

Context

From software decisions to physical behaviour

LUNA is built on the Hiwonder TurboPi platform around a Raspberry Pi 4B. Zhirui Lu and I combined Python control software, a wireless interface, computer vision, offline voice interaction and PID-tuned movement.

Software decisions became visible in the robot’s movement. Camera conditions, repeated voice commands and physical hardware faults all affected how it behaved, so testing at the bench was as important as reviewing the code.

My work covered hardware setup and repair, Raspberry Pi hardware integration, WonderEcho voice-command handling, and a controller that starts and stops the line-following routine through voice commands. I also supported Flask command routing, refined the PID tuning after Zhirui’s initial implementation, and contributed documentation. Zhirui developed the Flask control workflow, ball tracking and initial PID implementation; final integration was shared.

What I built

Subsystems sharing one Raspberry Pi

The integration challenge was connecting manual control, voice commands, line following and ball tracking through a shared movement system. WonderEcho communicates over I²C; the camera supplies visual input; Flask exposes wireless control. Python, OpenCV, NumPy and Tkinter support the control and diagnostic tools.

Vision OpenCV — line following, colour tracking, tag detection Voice WonderEcho over I²C, offline recognition, no network Control Flask web interface for wireless operation Movement PID-tuned drive with mecanum wheels Interface Tkinter for local diagnostics

The integration work centred on command routing and physical response. My WonderEcho handler maps recognised command IDs to actions and uses debounce logic to reduce repeated triggering. The voice controller starts and stops the existing line-following routine; it does not claim authorship of the underlying vendor routine.

What broke

Physical failure modes

  1. Movement needed practical tuning. Camera-based tracking can jitter or overcorrect. Zhirui implemented the initial PID control, and I refined the settings through physical testing.
  2. A hardware fault interrupted development. A motor problem and damaged wheel affected movement. I inspected the hardware and reworked available motor parts so the robot could continue operating.
  3. Voice commands needed more than recognition. The handler had to map command IDs, manage repeated input and trigger the intended movement. Repeated command testing checked the robot’s response.

This project taught me to record decisions while debugging instead of reconstructing them afterwards. I carried that habit into the HomeLab build log.

What I’d change

What I would change

  1. Design the arbitration first. I would define how manual, voice and autonomous commands share control before building each feature. Clear priorities and stop behaviour would make integration easier to reason about.
  2. Instrument it from the start. I would record command and processing timings earlier so that integration problems could be investigated with observations rather than repeated guesses.
  3. Define degradation explicitly. I would specify what the robot should do when a camera frame, sensor value or voice command is missing, before implementing the normal path.
