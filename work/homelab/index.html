ITDR Home Lab

A Wazuh SIEM with a Sysmon-instrumented Windows endpoint, built on one laptop and documented while it was going wrong.

Started June 2026 Status Phase 1 complete, development paused Stack Wazuh 4.9.2 · Sysmon 15.20 · Ubuntu 22.04 · Windows 11 · VMware Type Personal project
Context

Why build one at all

Every blue-team job description asks for SIEM experience, and no student has it, because SIEMs live inside companies. The way around that is to run one yourself and treat it as infrastructure rather than a tutorial: enroll a real endpoint, generate real telemetry, and keep it running long enough for its actual failure modes to show up.

ITDR — identity threat detection and response — is the specific lane. Most of what an attacker does after landing on a workstation shows up as identity and process behaviour before it shows up anywhere else, and that behaviour is exactly what Sysmon records.

What I built

Two machines and everything between them

An Ubuntu Server 22.04 virtual machine running a Wazuh 4.9.2 all-in-one deployment: indexer, server and dashboard on one host. A Windows 11 Enterprise virtual machine as the monitored endpoint, with Sysmon 15.20 installed and configured against the SwiftOnSecurity ruleset. Both on a Lenovo ThinkPad under VMware Workstation, bridged onto the local network.

Phase 1 was complete once the agent enrolled, telemetry reached the indexer, and I could log into the dashboard and watch events from the Windows machine arrive in something close to real time. That sounds like a small milestone. Getting there took four separate failures.

Fig. 1 — where telemetry goes. The endpoint is the only node that generates data; everything to the right of it stores, analyses or presents that data.

Component roles, since the naming is not obvious

Indexer Elasticsearch-based storage for parsed events Server Analysis engine — decoders, rules, alerting Dashboard Kibana-based interface for search and triage Agent Runs on the endpoint, ships Windows Event Channel data Sysmon Generates the process, network and file telemetry the Windows log does not produce on its own
What broke

Four faults, in the order they happened

These are the entries from the build log as they were written, not tidied up afterwards.

SymptomDiagnosisFix
VM storage corrupting OneDrive was syncing the directory holding the virtual disks and taking locks on .vmdk files mid-write. Moved every VM file outside the OneDrive tree. Cloud sync and files that write continuously do not belong in the same folder.
Server unreachable A stale netplan configuration held a static address of 192.168.170.10, from a subnet that stopped existing when I changed network adapters. The interface came up; nothing could route to it. Rewrote netplan against the bridged adapter. Found by comparing the configured address against the adapter’s actual subnet instead of debugging the services on top.
Indexer stalling The virtual disk hit 99% of 50 GB. The indexer degrades quietly under disk pressure rather than failing loudly, so this presented as a performance problem and wasted an hour before I checked df. Expanded to 100 GB via LVM with no rebuild. Now I size for retention rather than for install.
SSH dead on NAT On NAT networking the host was unreachable over SSH while the agent still enrolled successfully, so the failure looked partial and I spent time on the wrong layer. Reverted to bridged to get the lab productive. NAT restoration on the correct subnet is documented and queued rather than abandoned.

The pattern across all four is the same, and it is the thing I actually took away: each one presented as a problem with the layer I was looking at, and was caused by a layer underneath. Storage corruption looked like VMware. Unreachable server looked like Wazuh. Indexer stalling looked like resourcing. Checking the layer below before debugging the layer in front of you is most of the skill.

What I’d change

Honest revisions

  1. Build the detection rules alongside the infrastructure, not after. I treated Phase 1 as plumbing and Phase 2 as the interesting part. That was the wrong split — without rules there was no way to tell whether the pipeline was actually carrying useful data or just carrying data.
  2. Size the disk for retention from the start. Fifty gigabytes is enough to install Wazuh and not enough to run it. That was predictable and I did not predict it.
  3. Generate adversarial telemetry deliberately. Ordinary use produces ordinary events. Atomic Red Team would have given me something to detect on day one rather than waiting for a real anomaly that was never going to arrive on a lab machine.
  4. Rotate credentials before writing anything public. The initial lab password lived in plaintext in my notes for longer than it should have. It is rotated now, which is the correct outcome and an uncomfortable thing to have learned by nearly publishing it.

Where it goes next

Phase 2 is detection-rule development and incident-response exercises against the endpoint. The lab is currently paused while university assessment and paid work take priority, which is a scheduling decision rather than an abandoned project. The environment still stands.
